# ต่ออายุโฆษณา

## กติกาที่ตกลง

- ต่ออายุล่วงหน้าได้ หรือชำระสำเร็จก่อนครบ 72 ชั่วโมงนับจากวันสิ้นสุดเดิม (เวลาสิ้นสุดแสดงเป็นเวลาประเทศไทย)
- ช่วง 3 วันยังคงป้ายและกันพื้นที่เดิม สถานะ `GRACE` ไม่มีคำสั่งนำออกในช่วงนี้
- การส่งคำขอเพียงอย่างเดียวไม่ขยายสิทธิ์ หากไม่ชำระทันกำหนดให้เปิดสัญญาใหม่ ต้องให้เจ้าหน้าที่ยืนยันนำป้ายออกก่อนคืนพื้นที่
- ชำระทันกำหนดแล้วรอเจ้าหน้าที่ตรวจ/อนุมัติภายหลังได้ โดยคงป้ายเดิมไว้ ไม่เลื่อนวันเริ่มรอบใหม่
- รอบใหม่เริ่มที่ `endsAt` ของรอบก่อน และบวก 30/90/180 วันตามรายการ หากอนุมัติล่วงหน้าเป็น `SCHEDULED`; เริ่มอัตโนมัติเมื่อถึงวันกำหนด
- ทุกครั้งสร้างคำสั่งซื้อและหลักฐานชำระใหม่ เชื่อมด้วย `renewalOfId`; ไม่แก้วันเริ่ม/สิ้นสุด ราคา หรือเลขอ้างอิงรอบเดิม

## ลูกค้าและเจ้าหน้าที่

จากรายละเอียดใน /account หรือหน้า checkout เลือก **ต่ออายุตำแหน่งเดิม** หรือ **เปลี่ยน / เพิ่มตำแหน่ง** ไปยังหน้าจองเดิมที่มีข้อมูลต้นฉบับให้แล้ว เว็บไซต์เดิมถูกล็อกไว้

ใช้ราคาปัจจุบันจากหลังบ้าน ไม่เชื่อยอดจากเบราว์เซอร์ แนบสื่อเดิมตามช่องให้อัตโนมัติ และตรวจเจ้าของไฟล์อีกครั้งเมื่อส่งคำขอ ช่องใหม่ต้องมีไฟล์ครบ ตำแหน่งเดิมยังเป็นสิทธิ์ของเจ้าของสัญญา แต่ช่องของลูกค้ารายอื่นยังถูกล็อก

ตำแหน่งเดิม: คำนวณ → ชำระ → ตรวจยอด → อนุมัติต่ออายุ ไม่ต้องผ่านรับงานติดตั้งซ้ำ ส่วนการเปลี่ยนตำแหน่งยังมีเตรียมงาน/ตรวจติดตั้ง และให้เจ้าหน้าที่ยืนยันสลับตั้งแต่วันเริ่มรอบใหม่ เพื่อไม่กระทบโฆษณารอบเดิม เมื่อต่ออายุแล้วให้ถอดเฉพาะตำแหน่งที่ไม่ได้อยู่ในรอบใหม่

แอดมินเห็นลิงก์สัญญาก่อนหน้า/รอบถัดไป วันที่ต่อเนื่อง ขั้นตอน และประวัติ พร้อมแจ้งเตือนคำสั่งซื้อต่ออายุใหม่ และรายการจ่ายทันที่ถึงรอบแล้วแต่ยังรออนุมัติ

## การชำระและการจัดเวลา

- เวลากันชำระเดิม (30 นาที simulation/PromptPay, 24 ชั่วโมงลิงก์ manual) ถูกจำกัดไม่ให้เลย 72 ชั่วโมงของสัญญาเดิม หากหมดเวลาแต่ยังอยู่ในช่วง 3 วัน เปิดคำขอใหม่ได้
- Simulation ใช้เวลารับผลสำเร็จฝั่งเซิร์ฟเวอร์; manual ใช้เวลาที่เจ้าหน้าที่ยืนยันยอด; PromptPay ใช้เวลาธุรกรรมจาก Inquiry เมื่อกำหนด timezone ที่ยืนยันกับผู้ให้บริการแล้ว หากไม่ทราบใช้เวลาตรวจพบ ไม่ใช้เวลาที่ลูกค้าส่ง
- หาก provider ยืนยันช้าหลัง hold หมด ต้องตรวจว่าเวลาชำระที่ยืนยันได้อยู่ในกำหนด พื้นที่ยังไม่ถูกจองใหม่ และป้ายรอบเดิมยังคงอยู่ จึงรับเข้าคิวตรวจยอดได้ มิฉะนั้นส่งตรวจคืนเงิน ไม่เปิดบริการจากหน้า return URL
- Reconciliation อยู่ใต้ advisory lock เดียวกับจอง/ชำระ/อนุมัติ ทำงานเมื่อมีคำขออ่าน/ดำเนินการคำสั่งซื้อหรือ poll แจ้งเตือน การไม่เปิดหน้าไม่เปลี่ยนวันเริ่ม/สิ้นสุด; ครั้งถัดไปจะตามสถานะให้ทัน มี scheduler endpoint เพิ่มเติม ดู SERVICE-OPERATIONS-SETUP.md ต้องตั้งงานทุก 5 นาทีบน hosting
- การเปลี่ยนสถานะไม่ใช่การสั่ง plugin WordPress ให้สลับ/ถอดป้ายอัตโนมัติ ยังคงเป็นงานเจ้าหน้าที่ตามระบบติดตั้งปัจจุบัน ไม่มีเรียกเก็บอัตโนมัติหรือเชื่อมรับเงินจริงในงานนี้

## Migration และการนำขึ้นระบบ

`20261106020000_ads_renewals` เพิ่ม FK nullable, index, partial unique index กันรอบต่ออายุซ้ำ และอนุญาต GRACE/SCHEDULED ไม่ backfill หรือเขียนทับสัญญาเก่า ไม่แตะ media/API/embed/ownership

ทดสอบ migration เฉพาะฐานข้อมูล local `127.0.0.1:55439/aurum_ads_test` ยังไม่ deploy Production

ก่อน Production: สำรอง DB และตรวจ restore ในสภาพแวดล้อมแยก, ทดสอบ migration กับสำเนาข้อมูล, หยุดรับคำสั่งซื้อ/อนุมัติช่วงสลับเวอร์ชันให้ทุก instance ใช้กติกาเดียวกัน, migrate ก่อนโค้ดใหม่, canary บัญชีทดสอบทั้ง 2 โหมดและ 72 ชั่วโมง แล้วเปิดรับงานต่อ ไม่มี worker ใหม่จึงไม่ต้อง drain worker แต่ต้องรอ HTTP งานชำระ/อนุมัติเดิมจบ

หาก rollback: หยุดสร้างต่ออายุ/รับชำระและคงตาราง/คอลัมน์/หลักฐานที่สร้างไว้ ห้ามใช้โค้ดเก่าจัดการ GRACE/SCHEDULED โดยตรงหรือย้อนสถานะเป็น ACTIVE จนตรวจรายการค้างเสร็จ ห้าม drop ข้อมูลต่ออายุหรือ restore ทับธุรกรรมที่เกิดหลัง backup

## หลักฐานทดสอบ

- `src/lib/ads-renewal.test.ts`: advance / exact 72h cutoff / 30,90,180-day continuity / payment hold cap
- `scripts/test-ads-renewals.ts`: isolated DB, ownership, concurrent duplicate protection, current price, same/change slots, grace occupancy, scheduled activation, late staff approval, original dates unchanged
- `scripts/test-ads-renewals-http.mjs`: authenticated HTTP, origin, source files, idempotency, mock payment → staff approval → SCHEDULED, customer/admin links and booking SSR
- Regression: payment simulation, mocked signed PromptPay, notifications, unit workflow/booking/filter tests

Scripts clean only their own fixture IDs. `--keep-preview` creates a temporary local UI fixture manifest, which must be cleaned after browser verification. Never use a production DB with these scripts.

ตรวจหน้าจอ Desktop จริง: ปุ่มต่ออายุจาก /account, ข้อมูลติดต่อ/ไฟล์เดิมที่กรอกไว้ให้, โหมดเพิ่มช่องเปลี่ยนยอด 1,500 → 3,000 บาท และแอดมินแสดงอนุมัติล่วงหน้า 3/3 ขั้นตอน พร้อมวันเริ่มเท่ากับวันสิ้นสุดเดิม ภาพ `artifacts/admin-renewal-scheduled.png` มาจาก fixture ทดสอบ ไม่มีการเปิดบริการจริง ทดสอบหน่วย 27 ข้อผ่านพร้อม local DB/HTTP และ regression ที่ระบุข้างต้น
