# คู่มือตั้งค่าระบบบริการ AURUM

สถานะ 6 พฤศจิกายน 2026: เจ้าของยังไม่มีบัญชี Gateway, Email หรือ SMS จึงเตรียมตัวเชื่อมต่อและหน้าจัดการไว้ **ไม่เปิดรับเงินจริงและไม่ส่งข้อความภายนอก** คู่มือนี้ไม่ใช่การยืนยันว่าผู้ให้บริการอนุมัติธุรกิจแล้ว

## หน้าที่ใช้งาน

| ผู้ใช้ | หน้า | ใช้ทำอะไร |
|---|---|---|
| ลูกค้า | `/account` | คำสั่งซื้อ ระยะสัญญา แจ้งเตือน โปรไฟล์และอุปกรณ์ |
| ลูกค้า | `/services/ads-banner/book` | เลือกพื้นที่ แนบสื่อ ใช้รหัสส่วนลด และส่งคำขอ |
| ลูกค้า | `/services/ads-banner/checkout/[id]` | ชำระ/ติดตามงาน หลักฐานติดตั้ง เปลี่ยน Artwork คำร้อง ต่ออายุ |
| ลูกค้า | `/account/orders/[id]/summary` | สรุปยอดและพิมพ์ PDF ผ่านเบราว์เซอร์ ไม่ใช่ใบกำกับภาษี |
| ลูกค้า | `/account/recovery` | ขอรีเซ็ตรหัสผ่านและยืนยันลิงก์อีเมล |
| ลูกค้า | `/account/website-services` | ส่งคำขอ Website API และติดตามข้อเสนอแยกจาก Ads |
| เจ้าหน้าที่ MANAGER/HEAD | `/admin/ads-orders` | คำสั่งซื้อแบบแถว ค้นหา และเข้าสู่รายละเอียด |
| เจ้าหน้าที่ MANAGER/HEAD | `/admin/service-operations` | คิวเกินกำหนด งานรอมอบหมาย สถานะ worker/email และ CSV |
| เจ้าหน้าที่ MANAGER/HEAD | `/admin/website-services` | ประสานและตอบคำขอ Website API |

## ขั้นตอนเจ้าหน้าที่

1. ตรวจยอดจากผู้ให้บริการและรับคำสั่งซื้อก่อนเริ่มงาน สลิปหรือหน้า return ไม่ใช่หลักฐานยืนยันยอดจากเซิร์ฟเวอร์
2. มอบหมายพนักงานที่มีสิทธิ์และกำหนดเสร็จ → รับงานติดตั้ง → แนบลิงก์หลักฐานทุกตำแหน่ง → ส่งตรวจ
3. ถ้าต้องแก้ไข ส่งกลับพร้อมข้อความถึงลูกค้า หากผ่าน อนุมัติเริ่มบริการ โดยเซิร์ฟเวอร์กำหนดเวลาเริ่มและสิ้นสุด
4. สัญญาแรกนับ 30/90/180 × 24 ชั่วโมงจากอนุมัติ รอบต่ออายุนับต่อจากวันสิ้นสุดเดิม ป้ายเดิมคงอยู่ในช่วงผ่อนผัน 72 ชั่วโมงและระหว่างรออนุมัติหากจ่ายทันกำหนด
5. การต่ออายุตำแหน่งและสื่อเดิมข้ามงานติดตั้งซ้ำได้ หากเปลี่ยนไฟล์/ลิงก์หรือตำแหน่งต้องผ่านติดตั้งและตรวจงาน การเปลี่ยนรอบก่อนถึงกำหนดยังไม่สลับป้ายเก่า
6. คำขอ Artwork: ตรวจสื่อ → อนุมัติ → เปลี่ยนจริง → แนบหลักฐานและยืนยัน ระบบเก็บ quote/ไฟล์ต้นฉบับและประวัติเดิมไว้
7. คำร้อง: สนทนาต่อเนื่อง แนบหลักฐาน ปิดเมื่อแก้แล้ว ลูกค้าเปิดใหม่ได้ การปิดคำร้องไม่ใช่การยกเลิกหรือคืนเงิน
8. คืนเงินแบบ manual ต้องคืนกับผู้ให้บริการจริงก่อนบันทึกเลขอ้างอิงและยอดเต็ม ระบบนี้ยังไม่รองรับการคืนบางส่วนหรือสั่งโอนเงินคืนอัตโนมัติ Sandbox เป็นผลทดสอบเท่านั้น

WordPress ยังคงเป็นการติดตั้ง/เปลี่ยน/นำออกโดยเจ้าหน้าที่พร้อมหลักฐาน ไม่มีคำสั่งอัตโนมัติไปยังเว็บไซต์จริง การขึ้นสถานะใน AURUM จึงต้องทำหลังงานบนเว็บไซต์เสร็จแล้ว

## 1. เตรียม Gateway

ทำตาม [PROMPTPAY-SETUP.md](PROMPTPAY-SETUP.md) โดยขอให้ 2C2P ยืนยันการรับบุคคลธรรมดาและเว็บไซต์ `aurum123.com` รวมถึงเว็บไซต์ปลายทางและเนื้อหาจริงทั้งหมด การระบุว่าเป็น PR ไม่ใช่การยกเว้นเงื่อนไขผู้ให้บริการ

ลำดับ: ขอประเมินร้านค้า → ส่งเอกสารในช่องทางผู้ให้บริการ → ขอ Sandbox → ใส่ key ใน secret manager → ตั้ง callback HTTPS → ทดสอบยอดถูก/ผิด จ่ายซ้ำ callback ซ้ำ/ล่าช้า หมดเวลา และคืนเงิน → ขอเปิด Live หลัง UAT และอนุมัติร้านค้า

ตัวเชื่อมต่อที่มีอยู่รองรับ **2C2P Sandbox เท่านั้น** และปฏิเสธ production runtime ยังต้องพัฒนา/ตรวจรับโหมด Live จากข้อกำหนดร้านค้าที่ได้รับจริงก่อนรับเงิน ห้ามแก้ URL หรือใช้ Live key กับ Sandbox เพื่อข้ามข้อจำกัด USDT ยังเป็นระบบจำลอง ไม่มี wallet สำหรับรับเงินจริง

`TWOC2P_TRANSACTION_UTC_OFFSET` เว้นว่างจนผู้ให้บริการยืนยัน timezone ของ `transactionDateTime` รูปแบบ `yyyyMMddHHmmss` เมื่อไม่ทราบ timezone ระบบไม่เดาย้อนเวลาชำระ เมื่อแจ้งผลช้า จะรับงานต่อได้เฉพาะชำระทันเวลาที่ตรวจสอบได้ พื้นที่ยังว่าง และป้ายรอบเดิมยังไม่ถูกนำออก มิฉะนั้นเข้าคิวตรวจคืนเงิน

## 2. อีเมลธุรกรรม

เตรียม adapter Cloudflare Email Service REST ไว้แล้ว ขั้นตอนผู้ดูแล:

1. เปิดใช้ Email Sending ในบัญชีที่ผู้ให้บริการอนุญาต ยืนยันโดเมนผู้ส่งและ DNS ตามหน้าตั้งค่าของบริการ
2. สร้าง API token เฉพาะบัญชีและสิทธิ์ส่งอีเมล ไม่ใช้ Global API key
3. ใส่ `CF_EMAIL_ACCOUNT_ID`, `CF_EMAIL_API_TOKEN`, `SERVICE_EMAIL_FROM` และ `SERVICE_PUBLIC_ORIGIN=https://aurum123.com` ใน secret manager
4. คง `SERVICE_EMAIL_ENABLED=false` จนทดสอบกับกล่องจดหมายที่เจ้าของควบคุม ตรวจ inbox/spam, ลิงก์หมดอายุ, ใช้ลิงก์ซ้ำ, bounce และการปิดอุปกรณ์หลังรีเซ็ต
5. หลังทดสอบจึงเปิด flag และ scheduler ไม่ส่งอีเมลจริงจากเครื่อง demo

อีเมลแจ้งคำสั่งซื้อส่งเฉพาะอีเมลบัญชีที่ยืนยันแล้ว Payload คิวเข้ารหัสด้วย `ENCRYPTION_KEY` เดิม ต้องสำรอง key และห้ามเปลี่ยนโดยไม่ re-encrypt ข้อมูลเดิม ลิงก์ยืนยัน/รีเซ็ตอายุ 30 นาที ใช้ครั้งเดียว การรีเซ็ตรหัสผ่านออกจากระบบทุกอุปกรณ์

`PENDING` รอส่ง, `ACCEPTED` ผู้ให้บริการรับคิว (ยังไม่ใช่ส่งถึง), `DELIVERED` ผู้ให้บริการรายงานส่งทันที, `BOUNCED` ปฏิเสธผู้รับ, `UNCERTAIN` ไม่ทราบผล ต้องตรวจผู้ให้บริการก่อนส่งซ้ำ ไม่ retry timeout โดยเดาว่ายังไม่ส่ง กล่องแจ้งเตือนในบัญชียังใช้งานได้เมื่ออีเมลปิด

อ้างอิง [Cloudflare Send email API](https://developers.cloudflare.com/api/resources/email_sending/methods/send/)

## 3. SMS สมัคร/เข้าสู่ระบบ

มี adapter Twilio Verify ใช้ `TWILIO_API_KEY`, `TWILIO_API_SECRET`, `TWILIO_VERIFY_SERVICE_SID` ให้สร้าง Verify Service และตั้งข้อจำกัดงบ/ประเทศในบัญชีผู้ให้บริการก่อน เปิดเมื่อทดสอบเบอร์ที่เจ้าของควบคุมสำเร็จเท่านั้น ถ้ายังไม่ตั้งค่า หน้าเว็บแสดงว่า SMS ยังไม่เปิดและใช้อีเมลสมัครได้ สมาชิกแบบเบอร์โทรสั่งซื้อได้โดยไม่ถูกบังคับกรอกอีเมล

ไม่ส่ง key, OTP, เอกสารยืนยันตัวตน หรือรหัสผ่านลง Git/แชต/ช่องหมายเหตุคำสั่งซื้อ

## 4. Scheduler

ตั้ง `SERVICE_WORKER_SECRET` เป็นค่าสุ่มอย่างน้อย 32 ตัวอักษร แยกจากรหัสระบบอื่น ตั้ง `SERVICE_WORKER_ORIGIN` เป็น origin ภายในที่เข้าถึงแอปได้ เช่น `http://127.0.0.1:3000` หรือ HTTPS ของแอป

ให้ hosting scheduler เรียก `npm run services:worker` ทุก 5 นาที โดยฉีด environment จาก secret manager สคริปต์ POST `/api/internal/service-worker` พร้อม Bearer header ไม่ใส่ key ใน URL ไม่ต้องเปิด browser ค้างไว้ ไม่ได้สร้าง scheduled automation ใน Codex

งานตรวจ: ผลชำระที่ค้าง (เมื่อ Sandbox เปิด), รอบสัญญา/ผ่อนผัน, แจ้งเตือนหมดอายุ, งานติดตั้งเกิน due date, คำร้องค้าง 24 ชั่วโมง และคิวอีเมล มี lock กันการรันซ้อนและประวัติ `ServiceWorkerRun` หากไม่พบ heartbeat เกิน 15 นาที หน้าแอดมินแสดงเตือน ต้องตั้ง monitor ภายนอกตรวจด้วย เพราะหน้าจอแอดมินเองแจ้งไม่ได้เมื่อแอปล่ม

## 5. ไฟล์และพื้นที่เก็บ

ตั้ง `ADS_UPLOAD_DIR` เป็น absolute path บน persistent volume ที่ทุก instance ใช้ร่วมกัน ห้ามใช้พื้นที่ชั่วคราวของ container สำรองพร้อมฐานข้อมูล ตั้งสิทธิ์เฉพาะแอปและผู้สำรองข้อมูล ไม่เปิด directory ผ่าน web server

ไฟล์ใหม่ตรวจชนิดจริง ภาพ decode ได้ จำกัดมิติ/จำนวนเฟรม; MP4 ตรวจโครงสร้างกล่องหลัก จำกัด 20 MB ต่อไฟล์และ quota เริ่มต้น 1,024 MB ต่อบัญชี (`ADS_UPLOAD_QUOTA_MB`) การตรวจนี้ไม่ใช่ antivirus หรือการรับรองว่า MP4 เล่นได้ครบทุก decoder

`npm run services:storage-audit` ต้องตั้ง DATABASE_URL เป้าหมายและ ADS_UPLOAD_DIR ชัดเจน รายงานอ้างอิงไฟล์กับคำสั่งซื้อ/Artwork/คำร้อง เป็น read-only ไม่ลบไฟล์ รายการเก่าไม่มีเวลาสร้างจัดเป็น legacy-retain การทำ retention จริงต้องกำหนดนโยบายและสำรองก่อน ห้ามลบจากอายุไฟล์อย่างเดียว

## 6. โปรโมชั่นและ Website API

รหัสส่วนลดใน `/admin/ads-banner` เป็นข้อเสนอสาธารณะ ปิดเป็นค่าเริ่มต้น กำหนดช่วงเวลา เปอร์เซ็นต์ จำนวนสิทธิ์ ใช้หนึ่งครั้งต่อบัญชี นับเมื่อส่งคำสั่งซื้อ ไม่คืนสิทธิ์อัตโนมัติ ยอดคำนวณบนเซิร์ฟเวอร์และ snapshot ลงคำสั่งซื้อ ข้อมูลเก่าไม่เปลี่ยนตามราคาใหม่ รายการจำลองใช้จำนวนสิทธิ์แยกจาก standard

Website API มีคำขอที่เชื่อมสมาชิกและราคา snapshot แยกตารางจาก Ads: รับคำขอ → ประสานรายละเอียด → ยืนยันข้อเสนอ → ปิด/ยกเลิกคำขอ เป็นการติดตามก่อนขาย ยังไม่มี checkout, การจดโดเมน, การสร้าง hosting, การ provision API หรือการต่ออายุ hosting อัตโนมัติ ต้องยืนยันข้อกำหนดผู้ให้บริการและสัญญาของบริการนี้แยกจากโฆษณา ห้ามใช้สถานะคำขอเป็นหลักฐานชำระ/สิทธิ์เล่นวิดีโอ

## 7. Migration, rollout และ rollback

- เพิ่ม schema ผ่าน `20261106030000_service_operations` และ `20261106040000_website_service_requests` ไม่มีการแก้ ID สื่อ URL/embed, ownership, quote หรือไฟล์ของรายการเดิม
- สำรอง DB และ upload volume แล้ว restore ลงฐานข้อมูลแยก ตรวจจำนวน/ความสัมพันธ์ก่อนนำขึ้นจริง local restore ทดสอบได้ 17 คำสั่งซื้อจาก snapshot ก่อน migration
- หยุดรับงานใหม่ชั่วคราวตามแผน rollout และ drain worker ที่กำลังทำงาน บันทึก invoice/รายการเงินที่ค้าง ไม่ตัด callback ทิ้ง
- รัน `prisma migrate deploy` บนเป้าหมายที่ตรวจแล้ว ตามด้วย generate/build จาก release เดียวกัน flag การเงินจริง/ส่งข้อความยังปิด
- Canary บัญชีทดสอบ: member ownership, manager permissions, จองซ้ำ, upload/download, quote, coupon, proof gate, renewal 72 ชั่วโมง, อีเมล one-use และ worker auth
- Rollback ให้ปิดการรับรายการใหม่/ส่งข้อความ หยุด scheduler รอ lease จบ คืนแอปรุ่นที่เข้ากับ schema โดยคงตาราง/หลักฐานใหม่ไว้ ไม่ drop ตารางหรือ restore snapshot เก่าทับรายการเงินที่เกิดหลัง backup
- ไม่เปลี่ยน worker สื่อ/การ transcode หรือ plugin API เดิมในชุดนี้ การ drain worker สื่อจึงไม่เกี่ยวข้อง; worker บริการตัวใหม่ต้อง drain ตามข้างต้น

ยังไม่ได้ deploy, migrate ฐานข้อมูล production, เปิดบัญชีผู้ให้บริการ หรือทดสอบเงินจริง เจ้าของเป็นผู้กด deploy ตามที่แจ้งไว้

## หลักฐานตรวจในเครื่องและขอบเขตที่ยังต้องทำ

ตรวจด้วยฐานข้อมูล Docker แยก `aurum_ads_test` และ `aurum_worker_ops_test` เท่านั้น ไม่ใช้ DATABASE_URL ของ production:

- Unit tests: ราคา/ส่วนลด, ขั้นตอนงาน, การต่ออายุและช่วงผ่อนผัน, การกันช่อง, เวลาแจ้งยอด Gateway, อีเมลจำลอง และอายุ session ผ่าน เพิ่มเคสเปลี่ยนสื่อในตำแหน่งเดิมต้องตรวจงานใหม่
- Integration: `test-service-operations.ts`, `test-website-service-requests.ts`, `test-ads-renewals.ts`, `test-promptpay.ts` ผ่าน รวมผลชำระล่าช้า/พื้นที่ถูกจองต่อ/คืนเงิน และการเก็บ quote เดิมไม่เปลี่ยน
- HTTP จริง: `test-service-operations-http.mjs` ผ่าน การเข้าสู่ระบบ, inbox ส่วนตัว, CSRF, ownership, progress, หน้าพิมพ์สรุป, session, คำขอ Website API, รายงาน MANAGER/CSV และ worker ที่ไม่มีสิทธิ์ถูกปฏิเสธ
- Worker จริง: `test-service-worker.ts` ผ่านบนฐานข้อมูลว่างอีกชุด รันครบหนึ่งรอบ บันทึก heartbeat และปฏิเสธ lease ที่รันซ้อน ไม่มีการส่งออกไปยังผู้ให้บริการ
- UI desktop: ตรวจศูนย์ปฏิบัติการ โปรไฟล์/สถานะอีเมล และคำขอ Website API; เปลี่ยนเป็นเว็บไซต์เดิมแล้วตัดค่า hosting ถูกต้อง ยังไม่ยืนยันการแสดงผลบนโทรศัพท์จริง
- Backup restore: สำรองก่อน migration แล้วกู้คืนฐานข้อมูลอีกชุดสำเร็จ 17 คำสั่งซื้อ ไม่ restore ทับฐานข้อมูลที่ใช้งาน
- Build/Lint/Types: production build หลังแก้ UI รอบสุดท้ายผ่าน (119 หน้า, เตรียม standalone และ Prisma runtime สำเร็จ, exit 0) ดู `artifacts/service-operations-build.log`; มีคำเตือนเดิมเรื่อง `<img>` ในหน้าบริการ Ads Banner

งานก่อนเปิดเงินจริง: บัญชีและการอนุมัติ Gateway, Live adapter/UAT, DNS/อีเมล, Twilio Verify, scheduler, persistent upload storage และตรวจ staging/canary ตามด้านบน งานติดตั้งป้าย WordPress และการจัดเตรียมเว็บไซต์ยังทำโดยเจ้าหน้าที่

ข้อจำกัดที่ต้องติดตาม: รายการคำสั่งซื้อสมาชิกยังดึงข้อมูลเป็นหน้ามารวมเพื่อกรองฝั่ง client, รายงานยังไม่ใช่การกระทบยอดบัญชีหรือสถิติประสิทธิภาพโฆษณา, storage audit ยังไม่ลบไฟล์อัตโนมัติ, และ Website API ยังเป็นคำขอก่อนขาย ไม่ใช่ checkout/ต่ออายุ hosting อัตโนมัติ

Dependency audit พบรายการระดับ high 2 รายการจากสาย `bittorrent-tracker → ip` เดิมของระบบ P2P ซึ่งยังไม่ได้แก้ในชุดบริการนี้ ไม่ใช้ `npm audit fix --force` เพราะจะลดรุ่น tracker และเสี่ยงกระทบสัญญาเดิม ต้องประเมินหรืออัปเดตส่วน P2P แยกก่อนประกาศพร้อม production ทั้งระบบ ผล unit/build ผ่านไม่ใช่หลักฐานว่า dependency ไม่มีช่องโหว่
